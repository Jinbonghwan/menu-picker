# 기술스택 설계 — 오늘 뭐 먹지?

## 1. 선택한 스택
| 영역 | 선택 | 이유 |
|---|---|---|
| 프레임워크 | Next.js (App Router, TypeScript) | 과제 지침에서 지정된 프레임워크. Vercel 배포와 가장 궁합이 좋음 |
| 스타일링 | Tailwind CSS | 클래스 기반으로 빠르게 UI를 조립할 수 있어 1시간 스코프에 적합 |
| 상태 관리 | React `useState` / `useRef` (내장) | 화면이 하나뿐이고 상태도 3개(카테고리, 표시값, 결과)뿐이라 별도 라이브러리 불필요 |
| 데이터 저장 | 없음 (코드 내 배열) | 메뉴 목록이 정적이고 자주 바뀌지 않아 DB 없이 구현 가능 |
| 배포 | Vercel | Next.js와 동일 회사 제품이라 설정 없이 바로 배포 가능 |

## 2. Supabase(DB)를 쓰지 않은 이유
과제 안내에는 "데이터베이스 필요 시" Supabase를 세팅하라고 되어 있다. 이번 앱은
- 메뉴 목록이 사용자마다 달라지지 않고
- 로그인/개인화 기능이 스코프에 없고 (기획서 4번 참고)
- 히스토리 저장도 이번 스코프에서는 제외했기 때문에

DB가 필요하지 않다고 판단해 Supabase는 도입하지 않았다. 추후 "최근 추천 기록"
기능을 추가한다면 그때 Supabase 테이블(`picks: id, menu, category, created_at`)을
연결할 계획이다.

## 3. 컴포넌트 구조 결정
- Server/Client 컴포넌트 구분: 뽑기 로직이 `useState`, `setInterval` 등 브라우저 상태를
  다루므로 `page.tsx` 전체를 `"use client"`로 선언. 데이터 fetching이 없어 서버
  컴포넌트로 분리할 이유가 없었다.
- Next.js 16 기준 App Router 문서(`node_modules/next/dist/docs`)를 확인해 최신 버전
  기준으로도 `"use client"` 지시어 사용법이 동일함을 검증했다.

## 4. 트레이드오프
| 결정 | 얻는 것 | 포기한 것 |
|---|---|---|
| DB 없이 정적 배열 | 배포 없이도 바로 동작, 설정 시간 0 | 메뉴 목록을 관리자가 코드 수정 없이 바꿀 수 없음 |
| 단일 파일 컴포넌트 | 빠른 개발, 파일 탐색 최소화 | 기능이 커지면 리팩토링 필요 |
| 라이브러리 애니메이션 대신 `setInterval` 직접 구현 | 의존성 추가 없음, 번들 크기 최소 | 정교한 이징(easing) 효과는 부족 |
